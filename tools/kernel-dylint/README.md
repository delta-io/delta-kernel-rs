# Kernel Dylint rules

These compiler lints resolve the defining crate, types, and functions. They catch aliases of
Kernel APIs and ignore unrelated APIs with the same names.

| Lint | Prefer |
|---|---|
| `kernel_named_nullability` | `StructField::nullable(...)` / `not_null(...)` for literal booleans |
| `kernel_expression_literal` | `lit(value)` over `Expression::literal(value)` |
| `kernel_null_literal` | `null_lit(data_type)` over `lit(Scalar::Null(data_type))` |
| `kernel_predicate_constant` | `Predicate::TRUE` / `FALSE` over `Predicate::literal(true/false)` |
| `kernel_vec_parameter_into_iterator` | Consider `impl IntoIterator<Item = T>` for a vector only consumed by one iterator pipeline |
| `kernel_data_type_parameter_into` | Consider `impl Into<DataType>` for a value only forwarded to a conversion constructor |
| `kernel_prefer_guard_clause` | Review a loop-tail `if let` with short skip work for a guard and flatter success path |
| `kernel_multiline_nested_calls` | Review nested call arguments when rustfmt wraps the combined invocation |

The lints emit warnings with help text. They do not apply edits or add imports. Runtime boolean
values and macro expansions are excluded. Helper implementations that delegate to the longer
constructors are excluded to avoid recursive advice. Use a narrow `#[allow(kernel_...)]` when a
test intentionally exercises a constructor.

The parameter rules are advisory. A warning identifies a narrow body pattern; it does not prove a
signature change benefits callers or preserves their type inference. Review public API and
function-pointer compatibility before changing a signature. Neither rule emits automatic edits.

## Parameter rule scope

Both rules require a simple, owned parameter binding and exactly one reference to it in the body.
They resolve type aliases and reject same-named unrelated types. Trait declarations, trait
implementations, foreign/exported functions, const/async functions, closure captures, and macro
expansions are excluded. Trait methods remain eligible for use through `dyn` without new generic
parameters.

The vector rule requires the standard `Vec` type and a resolved `IntoIterator::into_iter` call,
either explicit or generated by `for`. It accepts a conservative list of standard `Iterator`
adapters ending in a known terminal consumer, plus the resolved `itertools::Itertools::join`
consumer. Vector indexing, borrowing, mutation, repeated use, iterator escapes, helper forwarding,
and operations requiring extra iterator capabilities such as `rev`, `len`, or `next_back` are
excluded. Plain `into_iter().count()` and every `.last()` path are left to Clippy. `count()` only
qualifies immediately after `filter` or `filter_map`, avoiding pointless map/count pipelines.
Other valid iterator patterns may be omitted.

The data type rule requires Kernel's `DataType` and one direct argument use in an audited Kernel
constructor: `StructField::{new,nullable,not_null}`, `ArrayType::new`, `MapType::new`,
`Scalar::null`, or `null_lit`. Cast constructors qualify only if their signatures already accept
the conversion bound. The rule checks the actual standard `Into<DataType>` bound on that argument;
it does not infer generic support from a method name. Clones, borrows, matches, storage, helper
forwarding, and multiple uses are excluded.

## Guard-clause rule scope

`kernel_prefer_guard_clause` is advisory and emits review candidates without edits. It recognizes
a plain `if let` at the end of an immediate loop body, with at least two top-level unit-valued
success operations and one to three short, nondivergent skip-work operations. The skip work can
become the guard's failure block followed by `continue`. The rule recognizes the compiler's
`for` and `while` control flow and requires the immediate loop body.

Retained postludes, call arguments, initializers, else-if/let chains, closures, explicit reference
bindings, `@`/or patterns, labeled exits, and macro-generated control flow are excluded. Logging
macros inside retained skip work are opaque statements. The loop-tail rule omits compound skip
work such as nested loops or conditionals. Function tails, explicit return/continue/break branches,
and diverging success paths are left to Clippy. The rule does not prove automatic equivalence:
review binding scope, temporary lifetimes, drop order, and observable behavior before applying the
suggestion.

## Nested-call rule scope

`kernel_multiline_nested_calls` is advisory. It considers an authored call or method invocation
whose argument list wraps and directly contains another call. The nested call may fit on one
line. Compact nested calls stay inline; one wrapped call with simple arguments does not warn.
Receiver-only fluent chains and multiline curried callees are excluded when their actual
invocation fits on one line. Only the outermost relevant call chain warns. Parentheses, borrows,
and `?` are transparent; `if`, `match`, short-circuit conditions, and closures are not traversed.

After finding a structural candidate, the rule runs the pinned toolchain's `rustfmt --check`
once per source file, using the crate edition and that file's project configuration. Child
modules are skipped by the probe, and it never writes files. Only already-formatted files warn;
unavailable formatters, unformatted files, `rustfmt::skip` scopes, macro-generated calls, and
const/static/const-fn contexts are omitted. Comment markers inside an invocation also suppress
it conservatively, including markers inside string literals.

The probe verifies the current formatter-wrapped layout. It does not prove that extracting a
particular argument will make the parent fit on one line. Named statements need review for
argument evaluation order, `?` propagation timing, conditional execution, and temporary, drop,
and borrow lifetimes. The rule proposes no automatic rewrite or general statement-length limit.

## Prefer Clippy when it covers the pattern

Before adding a custom rule, check Clippy's lint catalog and compile a representative example
with the relevant stock lints enabled. These advisory rules cover narrower gaps:

| Custom rule | Clippy coverage and remaining gap |
|---|---|
| Owned iterator parameter | `ptr_arg` concerns borrowed containers; `needless_pass_by_value` concerns unconsumed values. This rule generalizes consumed vector parameters. `iter_count`, `suspicious_map`, and `double_ended_iterator_last` cases are excluded. |
| `Into<DataType>` parameter | The value is consumed by a verified conversion-bound constructor; Clippy's borrowing suggestions do not propagate that bound to the wrapper's signature. |
| Loop skip-work guard | `manual_let_else` covers initializer extraction. `needless_return`, `needless_continue`, `redundant_else`, `never_loop`, and `while_let_loop` own the explicit-exit cases; only loop-tail skip work remains custom. |
| Formatter-wrapped nested calls | `excessive_nesting` measures nested blocks and item scopes. It does not check formatter-wrapped call arguments or propose named intermediate statements for this layout. |

## Run

Install the pinned compiler and Dylint CLI:

```sh
rustup toolchain install nightly-2026-07-20 --profile minimal \
  --component rustc-dev --component llvm-tools --component rustfmt
cargo +nightly-2026-07-20 install cargo-dylint dylint-link --version 6.4.0 --locked
```

Run from the repository root:

```sh
python3 tools/kernel-dylint/test.py
cargo dylint --path tools/kernel-dylint --fail-on-no-libraries \
  -p delta_kernel -- --lib --all-features --locked
```

Dylint builds and loads the library with its pinned nightly. The library and fixture have
independent Cargo workspaces and lockfiles so this compiler dependency does not change Kernel's
MSRV or root lockfile. `CARGO_TARGET_DIR` can keep these builds separate from normal Kernel builds.

The fixture test fails if any expected warning is missing, if a negative example warns, or if
Dylint changes either standalone lockfile. It uses the real Kernel crate and covers aliased
types/functions, local lookalikes, runtime booleans, preferred constructors, explicit suppression,
and generated code.

The parameter fixtures also compile representative proposed generic signatures with arrays and
container data types, and cover borrowed/multiple uses, iterator capability requirements,
captures, trait object boundaries, foreign functions, and already-generic parameters. Guard-clause
fixtures cover loop skip-work positives and Clippy-owned function/exit cases as negatives, plus
retained postludes, nested loops and closures, expression contexts, and already-guarded code.

Nested-call fixtures include a real Kernel enum constructor, `?` and borrow wrappers, a one-line
child whose combined call wraps, compact/fluent/conditional/closure negatives, and skipped
formatting. The harness generates a separate unformatted crate to check suppression and prove
the formatter probe leaves the source unchanged.

The repository check above is a manual audit: advisory findings remain visible at warning level.
CI rejects constructor warnings in the Kernel library and explicitly allows the four advisory
rules in its production check so existing review candidates do not fill every PR's CI log:

```sh
DYLINT_RUSTFLAGS='-Dkernel_named_nullability -Dkernel_expression_literal -Dkernel_null_literal -Dkernel_predicate_constant -Akernel_vec_parameter_into_iterator -Akernel_data_type_parameter_into -Akernel_prefer_guard_clause -Akernel_multiline_nested_calls' \
  cargo dylint --path tools/kernel-dylint --fail-on-no-libraries \
  -p delta_kernel -- --lib --all-features --locked
```

The fixture step leaves these lints at warning level to check expected diagnostics and clean
negative examples. The production step enforces the constructor lints and suppresses the advisory
rules; unrelated nightly warnings are unaffected. Run the manual audit above
without `DYLINT_RUSTFLAGS` to inspect advisory findings.
